ML FOUNDATIONS · 2 MIN READ

Your first model should be a baseline.

Give every experiment something meaningful to beat.

An experiment becomes easier to judge when the simplest useful comparison is already on the table.

Start with a reference point.

In classification, a dummy model can predict the most frequent training label without using the input features. Scikit-learn’s DummyClassifier provides this kind of reference. It helps answer a basic question: does the new model improve on a simple rule?

Illustrative example: if 95 of every 100 records belong to one class, always predicting that class gives 95% accuracy while missing the minority class completely.

Choose what “better” means.

Accuracy alone can hide important errors. Look at the confusion matrix and select metrics appropriate to the decision: precision for the reliability of positive predictions, recall for how many positive cases are found, and a suitable combined measure where useful.

Keep the comparison fair.

Evaluate the baseline and candidate on the same split and metric. Record the data snapshot, preprocessing, parameters, and results. A more complicated model should justify its extra development and maintenance cost.

My practical checklist is small: define the prediction task, choose the split, establish a baseline, then inspect where the candidate still fails. Improvement is more persuasive when its reference point is visible.

ML FOUNDATIONS · 2 MIN READ

Data leakage is an engineering bug.

A stronger score is only useful if the evaluation is credible.

A model can look excellent for a simple reason: the evaluation boundary was crossed before the experiment began.

The quiet failure in preprocessing.

Suppose a scaler is fitted on the full dataset before the train/test split. Its learned statistics now include test data. The model’s evaluation no longer represents a fully unseen sample. Feature selection and imputation can introduce similar problems.

Move the boundary earlier.

Split before fitting transformations. Learn preprocessing from the training partition and apply those fitted transformations to validation or test inputs. During cross-validation, preprocessing needs to be learned within each training fold.

The useful question is: would this information actually exist when the prediction is made?

Make the safe path repeatable.

A scikit-learn Pipeline combines transformations and an estimator. When used correctly with cross-validation, it keeps those operations inside the relevant fit boundary and makes it harder to accidentally apply a different preprocessing sequence.

I think of leakage checks as part of the experiment’s engineering contract. Inspect the feature provenance, split logic, and transformations alongside the model. A credible result needs a credible process.

03
APPLIED AI · 2 MIN READ

An agent needs a stopping rule.

Design a useful end state, alongside tool selection.

Connecting a model to tools is only the beginning. The application also needs to know when enough work has been done.

Treat the limit as a signal.

An agent reaching an execution limit may be doing legitimate multi-step work, or it may be repeating an unproductive cycle. LangGraph’s documentation recommends inspecting unexpected cycles; increasing a recursion limit is appropriate only when the graph genuinely needs additional steps.

Define completion in application terms.

For a weather assistant, a useful completion rule could be: the location is resolved, one valid weather result is available, and the response has been assembled. A failed tool call should lead to an explicit retry or a clear explanation.

Suggested design: define success, define the retry budget, and define the result returned when that budget is exhausted.

Leave an inspectable trace.

My preferred debugging record includes the selected tool, its arguments, the outcome, and the reason execution continued. Repeated actions without new information are a useful warning sign.

These are application design recommendations, not guarantees from a framework. A good agent experience includes a useful failure path as well as a successful answer.
